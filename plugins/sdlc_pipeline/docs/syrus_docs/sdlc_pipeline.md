# SDLC Pipeline

The SDLC Pipeline plugin adds a full-width **Pipeline** tab to each repository. It derives one mutually exclusive, furthest-proven stage for each visible Job from authoritative Job state, landed commit, and configured deployment-stage evidence. It never stores a parallel pipeline state.

The ordered lifecycle is Triaging, Ready, Implementing, Review, Landing, and Landed, followed by the repository's `.syrus.yml` `deployment_stages` in declared order. Each stage reports totals, attention and aging counts, oldest age, and at most five highlighted Jobs. Epic and ungrouped totals make the overview useful without returning every Job.

The full-width board scrolls horizontally without moving when its 30-second refresh runs. Soft edge masks, previous/next controls, a stage navigator, and left/right keyboard navigation expose offscreen stages. Pinned work, attention items, and recent changes are promoted above ordinary work; the rest remains compressed into linked Epic and ungrouped aggregates. Selecting a stage opens a keyboard-safe, paged, bounded list. Cards link to the existing Job summary, latest Workflow, and delivery/release evidence on the Job instead of duplicating those controls. Deployment lanes are explicitly observational: their placement comes from recorded delivery evidence and cannot be changed or dragged on this page.

Landed remains a separate lane before any configured deployment stages, making the deployment gap visible. A warning identifies partial delivery evidence when work has not reached the final configured stage. The final configured delivery stage is explicitly marked as the bounded recent-release tail; older entries fade modestly by release age, with a contrast floor, while evidence type remains explicit. With no `deployment_stages` configuration the lifecycle and Landed lanes still work and the page explains how to enable delivery evidence. Loading, empty, filtered-empty, and API-error states are rendered in place, including a retry action.

`GET /api/v1/app/repositories/:repository_id/sdlc_pipeline` returns the bounded overview. Pass `stage=<stage-key>`, `page=<number>`, and `limit=<1..50>` for bounded drill-down. Terminal work is limited to the 50 most recently completed Jobs from the last 30 days. The endpoint requires an authenticated user with access through `Repository.accessible_to(Current.user)` and additionally applies `Job.visible_to(Current.user)`.

The FilterBar selects the Job cohort before stage totals, Epic aggregates, highlighted cards, and drill-down rows are calculated. It supports nested AND/OR/NOT expressions for search, associated chat, Epic, Job, and owner. Repository scope comes from the route and is never persisted in a saved view. Pipeline stage and lifecycle state are deliberately not filter fields, so configured stages remain visible even when empty. The built-in **All** and **Mine** views use the same editable AST as user-defined SmartFolders; historical range, scroll, and other presentation state are not saved.

The response includes placement evidence for every returned item: its lifecycle state, landed SHA, or deployment-stage status and timestamp. Repository deployment configuration is read at request time, so edits are reflected without a refresh job or cache-owned state.

The same response includes a bounded historical envelope for the filtered cohort: a checkpoint followed by ordered stage-change deltas and meaningful event ticks. The default range is seven days and requests are capped at 90 days, 500 Jobs, and 2,000 deltas. `range_start` and `range_end` select that envelope; the URL-backed `at` value is presentation state only and is deliberately excluded from SmartFolders and API cache keys. Scrubbing reconstructs stage totals and Epic aggregates in the browser without a request for each movement. Historical cards explicitly label their stage as reconstructed while retaining current Job titles and metadata, because mutable metadata that was not recorded historically cannot be reconstructed. A bounded result says so in its accuracy metadata.

Historical mode is read-only, has a persistent banner and Return to now action, and continues polling current data without moving the stage scroller. The dedicated time rail supports keyboard operation through the native range control and respects the existing reduced-motion behavior; horizontal controls remain exclusively stage navigation.

Disabling or deleting the plugin removes the tab, endpoint, frontend module, translations, and this documentation. Jobs, Epics, landing records, and deployment-stage statuses remain untouched.
